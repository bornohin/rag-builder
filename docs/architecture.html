Plate 01  ·  The idea

Code search an agent can actually act on.

A recipe for indexing any codebase so an AI assistant stops guessing and starts citing. Two search engines run side by side, their results are merged, and every answer comes back with an exact file and line range. It all runs on one laptop, with no server and no network.

Input

Any repository, any language.

Output

path/file.ext:120‑168 plus the code that lives there.

Runs on

CPU only. No GPU, no API key, no daemon.

Talks to

Any assistant, over a standard tool protocol.

Plate 02  ·  The problem

Two kinds of search, two kinds of blindness.

Every code search tool is one of these. Each fails on exactly the questions the other one answers, which is why picking one is the wrong move.

Keyword search  /  grep

Finds the letters you typed.

Perfect when you know the name. Useless when you don't: ask it “how does login work” and it looks for files containing the word “login”. It cannot tell that authenticate() is the answer.

Meaning search  /  embeddings

Finds things that seem related.

Great at vague questions. Unreliable at precise ones: ask for the exact symbol refresh_token_v2 and it may hand you five things that are merely about tokens, and miss the one that is it.

So run both, always, and combine the two ranked lists. That single decision is what the rest of this deck is built around.

Plate 03  ·  The pipeline

From files to a cited answer.

Five stages. The first three happen once, when you index. The last two happen every time the assistant asks a question.

Plate 04  ·  Stage 2

Cut code where the code cuts.

Search engines work on chunks. How you cut them decides whether a result is useful. The naive method slices every N lines; the better method uses a real parser and cuts on function and class boundaries.

Rule 1

A chunk is a function, class, or statement — whatever the language calls a unit.

Rule 2

Too big to embed? Split it into labelled parts rather than truncating it.

Rule 3

Anything the parser skipped still gets indexed, so no line is ever lost.

Plate 05  ·  Stage 3

Index the same chunks twice.

Both indexes are built from one chunk list, so a hit in either can be traced to the same lines of code.

Index A  /  meaning

Turn each chunk into a list of numbers.

A small model that runs on the CPU converts text into coordinates. Chunks about similar things land near each other, so a question can be turned into coordinates too, and you look up the nearest neighbours.

Catch: the model has a size limit. Measure chunk length with the model's own counter — guessing from character count silently chops the ends off your longest chunks.

Index B  /  exact text

Count words, rank by rarity.

A classic keyword ranker. Rare words in a short chunk score highest, which is exactly the behaviour you want for a distinctive function name.

Catch: split identifiers the way programmers write them. Store getUserToken whole and as get​/​user​/​token, or a search for one form never finds the other.

Both indexes must use the same word-splitting rules at index time and query time. A mismatch here is invisible — nothing errors, results are just quietly worse.

Plate 06  ·  Stage 4

Merging two rankings.

Each index returns its own ordered list. Their scores are on different scales and cannot be compared — but their positions can. Score every result by where it placed, then add the scores up.

Refinement

Weight the two lists by question shape. A bare identifier should trust the keyword side; a written-out question should trust the meaning side.

Refinement

Nudge up any chunk whose own name is a word the user typed. Rank alone cannot express “this chunk is the thing you asked for”.

Plate 07  ·  Stage 5

Handing it to the assistant.

The index is exposed as a small set of tools over a standard protocol, so any assistant can use it without custom glue. Each tool answers a different shape of question — and says so clearly enough that the model picks the right one.

Tool

Search

“Where is X implemented?” Runs both engines, merges, returns signatures plus exact line ranges.

Tool

Find a symbol

Where a name is defined and where it's used, definitions ranked first.

Tool

Literal search

Searches the live files, not the index. Proves a string exists — or truly does not.

Tool

Read lines

Pull exact ranges from many files in one call, instead of many reads.

Tool

Status

How big the index is, when it was built, and which files have drifted since.

Tool

Refresh

Re-index after edits. Only changed files are redone.

Two habits worth copying: return a compact preview by default and let the model ask for the full body, so context isn't wasted — and when the index looks out of date, say so in the result instead of answering confidently from stale data.

Plate 08  ·  Keeping it true

An index is only as good as it is current.

Rebuilding everything after each edit is too slow to run often, so it doesn't get run — and a stale index is worse than none, because it is confidently wrong.

Trap

A long first build that crashes at 90% and restarts from zero. Save progress periodically so it resumes.

Trap

Auto-refresh wired into one repository while the others drift silently.

Trap

Touching a colleague's uncommitted work. Never pull a dirty checkout — skip it and say why.

Plate 09  ·  Scale

What breaks first, and when.

This design holds comfortably into the tens of thousands of chunks. Past that, the limits arrive in a predictable order — and none of them is the vector search.

What gives out Why Roughly when What to do
Memory Every chunk's text is held in RAM for the life of the server ~300k chunks Keep text on disk; load only the results you return
Scanning for a symbol Checks every chunk one at a time ~250k chunks Build a name → chunk lookup while indexing
Keyword ranking Pure interpreted loops over the whole corpus per query ~250k chunks Swap in a real inverted index
Saving the index The whole file is rewritten even for a one-line edit ~150k chunks Write per-file records instead of one blob
First build time Embedding is the slow step and it is one-off hours, at millions of tokens Checkpoint it; split the work per project

Two numbers worth knowing before you plan: chunk count is driven by how many symbols your code has, not by total size divided by chunk size — expect several times more chunks than a windowing estimate predicts. And token counts differ by model, often by 25–30%, so count with the tokenizer you will actually use.

Plate 10  ·  The recipe

Ten steps, any repository.

  1. 01

    Survey before you build

    Find the generated files, lock files and build output. Excluding them is the cheapest quality win available.

  2. 02

    Put every setting in one file

    Paths, model, exclusions, word-splitting. Both the indexer and the server read from it, so they cannot drift apart.

  3. 03

    Chunk with a parser

    Cut on functions and classes. Record exact start and end lines on every chunk.

  4. 04

    Measure length with the real tokenizer

    Character-count estimates silently truncate your densest chunks.

  5. 05

    Build both indexes from the same chunks

    Meaning and exact text. Same word-splitting at index and query time.

  6. 06

    Merge by rank, not by score

    Then weight by question shape and boost exact name matches.

  7. 07

    Hash files so rebuilds are incremental

    And save progress during long builds so a crash resumes.

  8. 08

    Serve it over a standard tool protocol

    No vendor-specific fields, so any assistant can use it.

  9. 09

    Make staleness loud

    Warn in the result itself. Confirm negative answers against the live files.

  10. 10

    Measure every constant you guard a resource with

    Batch sizes, result limits, safety caps. A confident comment above a guessed number is still a guessed number.
